        1. Executive summary and mission
        1.1 The mission
        ECLIPSE is a Windows-native, hardware-aware AI model inspection, preparation, optimization, and
        inference platform. Its purpose is to make the strongest practical use of large open-weight models on a
        computer that cannot hold or run those models in their original form.

        The primary objective is maximum useful intelligence at interactive generation speed. ECLIPSE is not merely
        a model downloader, quantizer, file converter, model viewer, or launcher. It is a coordinated system that
        studies a model before execution, chooses how it should be represented, plans where its pieces should live,
        schedules work across CPU/GPU/RAM/VRAM/storage, and measures whether the result is both fast and
        capable.

        1.2 What counts as success
          The system can inspect supported model files without running the full model locally.
          It identifies the real architecture, tensor inventory, precision, expert structure, and memory requirements
               instead of guessing from a model name or parameter count.
          It builds a reproducible execution plan for the actual computer and explains which models/configurations are
               viable, marginal, or unrealistic.
          It achieves the best measured sustained generation rate and response latency available for a given model,
               without pretending that cold SSD streaming is equivalent to fast memory residency.
          It preserves important capabilities and measures any losses from compression, approximations, or
               optimization.
          It stays within configured RAM/VRAM limits, avoids uncontrolled Windows paging, and keeps the PC usable.
          It evaluates completed, verified work - not only tokens per second.

        1.4 The central correction
        The design cannot depend on the user first running a huge model locally. A model that does not fit is
        precisely the model ECLIPSE needs to inspect. Therefore the first major subsystem is static model
        intelligence: read the checkpoint and its metadata in bounded chunks, map the architecture and weights,
        and produce a model atlas without full-model inference.

        Runtime activation tracing, live routing observation, and learning from the model’s actual token-by-token
        behavior are valuable later additions. They are not prerequisites for the first usable design or the first local
        inference milestone.

        2.2 User-facing constraints
          Windows-first and free/open-source wherever practical. No mandatory paid inference APIs or cloud service.
          No Linux/WSL dependency for the core workflow. Optional backends can be evaluated separately, but the
               baseline path must be Windows-native.
          The interface should be approachable to a beginner: plain language, clear status, safe defaults, and
               explanations before risky changes.
          Use established, maintained projects and pinned dependencies where practical. ECLIPSE should orchestrate
               proven building blocks instead of rebuilding every kernel.
          Preserve original model files. All preparation outputs and experiments must be separate, named, and
               reversible.
          Store logs, diagnostics, manifests, experiment results, and a root STATUS.md in the project folder.


        2.3 Design assumptions
        ECLIPSE initially targets open-weight models and formats whose architecture and weights can be legally and
        technically inspected. It does not assume access to the private original weights of closed models such as
        proprietary hosted services. It does not claim to recreate a closed model from its outputs.

        A model’s total parameter count is not enough to predict performance. Architecture, active parameters,
        quantization format, layer dimensions, memory access pattern, kernel implementation, prompt length,
        context cache, and actual memory bandwidth all affect the result.

        3.2 Why putting a giant model on an SSD is not enough
        An SSD is excellent for storing large models and for loading or prefetching data. It is much slower than
        VRAM and usually slower than RAM for the fine-grained, repeated access needed during decoding. If every
        generated token requires reading many gigabytes of expert weights from storage, the system becomes
        storage-bound. The fact that the complete model fits on disk does not mean it can generate quickly.

        Colibri’s public benchmark notes provide a useful warning example: its documented cold GLM-5.2 path
        estimates about 11 GB of disk reads per token and roughly 0.05-0.1 tokens/second on a drive around 1 GB/s.
        The same project reports much higher results when experts are resident in RAM/VRAM, including a six-
        RTX-5090 experiment. These are measurements from that project’s configurations, not predictions for this
        PC.


        3.3 The working-set principle

         CORE ENGINEERING RULE Optimize the weights and data actually needed for the next token - the working set
         - rather than merely maximizing the total number of parameters that can be stored somewhere.


        For a Mixture-of-Experts (MoE) model, only some experts are selected for a token, although shared layers
        and routing logic may also be required. If the selected experts are already in RAM or VRAM, ECLIPSE may
        avoid a large storage penalty. If the selected experts are cold on SSD, prefetching can help only when the
        system has enough lead time and bandwidth. The router’s actual selection remains authoritative.


        3.4 Why no single trick fixes everything
          Quantization reduces memory use and data movement but can reduce quality; lower bit width does not
               automatically mean higher speed on every GPU.
          Offloading increases capacity but can increase transfer time and CPU involvement.
          Pruning can reduce work but may remove useful capacity or alter model behavior.
          Caching avoids repeated transfers only when future requests reuse cached data; workload changes can defeat
               simple frequency assumptions.
          Predictive prefetch can hide some transfer latency but cannot guarantee that a prediction is correct or replace
               the model’s router decision.

        The system must treat these as interacting choices and measure the combined system, not optimize each one

        4. ECLIPSE design constitution
        These rules govern every subsystem, experiment, and future feature. A feature that violates them should not
        become a default path.

         1. Never require the original oversized model to run locally before ECLIPSE can inspect or prepare it.
         2. Optimize for interactive output speed and useful capability, not merely successful loading.
         3. Treat 10+ sustained tokens/second as a goal to test, not a result to claim without measurement.
         4. Minimize routine SSD-to-weight transfers during token generation.
         5. Maximize useful GPU and RAM residency while preserving Windows headroom.
         6. Never overwrite or modify the user’s original model weights.
         7. Never assume quantization, pruning, or compression automatically improves speed.
         8. Never sacrifice intelligence without measuring which capabilities changed and by how much.
         9. Never replace actual router-selected experts with predicted experts.
         10. Never publish a speed improvement without a reproducible benchmark.
         11. Use teacher-independent verification wherever practical; do not require the original giant model for
               every test.
         12. Add runtime learning only after a workable inference path exists.
         13. Protect Windows responsiveness and prevent uncontrolled paging.
         14. Do not make paid APIs, remote compute, or subscriptions mandatory.
         15. Automate hardware detection, budgets, model preparation, and configuration selection with safe
               overrides.
         16. Measure verified useful work completed, not just token throughput.

        5.2 End-to-end lifecycle
         1. Import a model folder or supported model file without loading the entire model into RAM or VRAM.
         2. Inspect metadata, tensor shapes, architecture, tokenizer, and checkpoint organization; create the Model
               Atlas.
         3. Estimate memory, bandwidth, compute, compatibility, and feasible execution paths for this PC.
         4. Prepare one or more reversible variants using the least destructive optimizations first.
         5. Build an execution manifest defining tensor layout, device placement, precision, cache policy, and
               memory budgets.
         6. Launch a proven inference backend through ECLIPSE’s orchestration layer.
         7. Measure real latency, token speed, resource use, storage traffic, and output quality.
         8. Use evidence to tune residency, prefetch, and precision. Add runtime observations only when supported.
         9. Keep the winning profile and its benchmark record; preserve failed experiments for diagnosis.


        5.3 Build around existing inference kernels
        ECLIPSE should own model inspection, planning, preparation policy, memory orchestration, measurement,
        and user experience. It should reuse established inference engines and optimized kernels whenever they are
        compatible. For example, llama.cpp documents CPU SIMD, CUDA, Vulkan, and CPU/GPU hybrid execution
        paths, as well as multiple quantization formats. Colibri is a specialized point of comparison for hierarchical
        MoE residency and SSD/RAM/VRAM scheduling.

        The exact backend choice must be decided by model format, operator support, Windows compatibility, GPU
        architecture, and measured performance. Do not assume a backend supports every model or every precision
        on the RTX 2060 Super. ECLIPSE should have a compatibility matrix and small smoke tests before
        committing to a path.

         DESIGN DECISION Do not build a new matrix-multiplication kernel library as the first project milestone. A new
         kernel is justified only when profiling identifies a specific gap that existing, maintained backends cannot meet
         and a test can prove the new kernel is faster and correct.

        inference
        6.1 The first major milestone
        The Laboratory is the foundation because the user cannot run a model that does not fit. Its first version must
        accept a model package and report what can be learned from the files alone. It must not attempt to allocate
        the complete parameter set into system memory or VRAM.

        6.2 Supported input formats
          GGUF files: parse metadata, tensor names, dimensions, tensor types, tokenizer information when present, and
               file layout.
          Safetensors: read headers and tensor metadata, then access tensor bytes by offset in bounded chunks.
          Hugging Face-style model folders: inspect config files, shard indexes, tokenizer files, generation configuration,
               and weight shards.
          Other formats only after a documented parser, test fixtures, and a safe failure path exist.


        6.3 Architecture discovery
        Extract and normalize what the checkpoint actually declares: architecture family, number of layers, hidden
        size, intermediate size, attention heads, key/value heads, head dimensions, vocabulary size, normalization
        and positional-embedding choices, layer types, and any multimodal components. For MoE architectures,
        discover expert count, experts per token, shared experts, router dimensions, and expert tensor shapes when
        represented in the metadata.

        The parser should distinguish confirmed facts from inferred details. If a model config is incomplete,
        contradictory, or custom, the Atlas should display “unknown” or “needs adapter” rather than silently
        assuming a familiar architecture.


        6.4 Weight and tensor analysis
          Inventory tensor names, shapes, dtypes, byte ranges, shard locations, alignment, and total byte counts.
          Analyze weights in bounded chunks, with a hard memory ceiling. Never read every tensor into RAM merely to
               inspect it.
          Calculate useful statistics where feasible: min/max, mean, standard deviation, norm estimates, histograms,
               sparsity patterns, outlier counts, and per-channel/per-block distributions.
          Compare related tensor groups and expert tensors for similarity or redundancy, while treating similarity as a
               candidate clue - not proof that weights can be merged or deleted.
          Record format limitations: a quantized checkpoint may not expose original full-precision values, and some
               quantization metadata or scales may be format-specific.


        6.5 Tokenizer and prompt interface inspection
        Record tokenizer type, vocabulary size, special token IDs, chat template, stop tokens, and any known context-
        window metadata. Flag missing or inconsistent files. A model that loads but uses the wrong tokenizer or chat
        template may behave incorrectly even if its weights are intact.

        6.7 What static inspection cannot tell us
        Static weights alone cannot reliably reveal which experts will be chosen for a particular prompt, the full
        distribution of activations under a real workload, actual end-to-end tokens/second, or exactly which
        capabilities a quantization will harm. Some statistical or layerwise analysis may estimate risk, but it is not
        the same as behavioral testing. ECLIPSE must keep these categories separate.

         NO LIVE MODEL REQUIRED The first Atlas, tensor inventory, static memory estimate, and initial compatibility
         report must be generated without launching inference or requiring the complete weights in RAM/VRAM.




        7. Model preparation and intelligence-aware compression
        7.1 Preserve the original
        The imported model is immutable from ECLIPSE’s perspective. Preparation writes new files to a separate
        output directory, records the source hash and tool versions, and provides a manifest describing every
        transformation. A failed run must not damage or partially replace the original checkpoint.


        7.2 Start with low-risk preparation
          Create indexed metadata and tensor lookup tables so the runtime can access tensors without repeatedly
               scanning large files.
          Use memory mapping or bounded file access where supported; avoid unnecessary copies and peak-memory
               spikes.
          Normalize tensor ordering and alignment only where the selected backend benefits and correctness can be
               tested.
          Group tensors and experts in a layout that supports contiguous reads and efficient transfer.
          Generate a manifest containing offsets, sizes, dtype, alignment, checksums, and device-placement hints.

        7.4 Quality-first optimization sequence
         1. Baseline: run a supported reference configuration and save output-quality and speed measurements.
         2. Lossless preparation: change indexing/layout only; verify numerical equivalence and benchmark.
         3. Conservative quantization: test one known-supported format at a time.
         4. Mixed precision: retain higher precision for sensitive tensors if evidence justifies the extra bytes.
         5. More aggressive quantization or structured sparsity: evaluate only after the safe path has a baseline.
         6. Capability correction: add only when testing identifies a repeatable weakness and a correction
               demonstrably helps.


        7.5 Compression is not automatically acceleration
        A smaller representation can reduce memory traffic and allow more weights to remain resident. But an
        unsupported or inefficient low-bit format can require expensive unpacking, dequantization, extra kernels, or
        CPU fallback. A lower-bit model may therefore run slower than a slightly larger format. The planner must
        evaluate actual kernel support and measured token speed, not choose the smallest file by default.


        7.6 Model preparation package
        Each prepared variant should include: source identity and hash; transformation history;
        quantization/configuration details; tensor manifest; compatibility checks; tokenizer/chat-template
        references; validation results; and a short human-readable report explaining expected trade-offs. Prepared
        variants should be reproducible from the documented command or UI action.

        8.2 Memory budget manager
        ECLIPSE should determine safe budgets from actual free resources at launch and monitor them during
        generation. The user can set maximum RAM and VRAM budgets, but the default must leave room for
        Windows, the desktop, browser tabs, and other foreground software. A run should not be considered
        successful if it achieves a benchmark by pushing the PC into constant paging or making the desktop
        unusable.


        8.3 Expert Residency Optimizer
        For MoE models, the engine can maintain a hierarchy of hot and warm experts. It should consider model
        layer, expert size, recent use, measured frequency under a task profile, router information when available,
        and transfer cost. The goal is to keep frequently selected experts in RAM/VRAM while moving less-used
        experts out of the fastest tiers.

          The router-selected experts are always the experts the model actually uses. A cache prediction is only a
               prefetch hint.
          If prediction is wrong, ECLIPSE must still fetch and execute the selected experts - never silently substitute the
               predicted experts.
          Track per-layer and per-expert hit rates, misses, load time, bytes transferred, and evictions.
          Do not assume a single global frequency table fits coding, math, and general conversation equally well.


        8.4 Predictive prefetch
        Prefetching attempts to load a likely-needed tensor or expert before it is requested. It may overlap storage
        reads and transfers with computation. In the first iteration, static metadata and simple observed access
        patterns can inform policy. After inference is possible, actual router outputs and runtime traces can improve
        decisions.

        A prefetch system needs confidence thresholds, bandwidth limits, cancellation, and priority handling. It
        should not flood the SSD, RAM, or VRAM with guesses. If a selected expert is not cached, correctness takes
        priority over speed.


        8.5 Workload-aware caching
        Cache policy should be evaluated against real workloads and changes between workloads. Candidate signals
        include recency, measured frequency, layer position, task profile, router confidence, expert transfer size,
        and observed hit/miss cost. LRU can be a baseline, not an assumed final solution. ECLIPSE should compare
        simple baselines with workload-aware and router-informed alternatives.

        8.6 CPU/GPU coordination
          Use asynchronous I/O and transfer queues where the backend supports them.
          Overlap data movement with independent computation only when correctness and dependency ordering are
               guaranteed.
          Avoid oversubscribing the i7-8700K. Reserve CPU capacity for Windows and foreground applications.
          Use GPU kernels for supported operations; CPU fallback must be visible in diagnostics because a fallback can
               become a major bottleneck.
          Profile the complete critical path: storage read, decompression/dequantization, RAM copy, PCIe transfer,
               compute, synchronization, and next-token scheduling.


        8.7 KV cache and context management
        KV cache stores the model’s attention history as a conversation grows. Its memory requirement depends on
        architecture, number of layers, key/value heads, precision, and context length. ECLIPSE should estimate it
        from actual architecture metadata and provide safe context options rather than blindly set the largest
        advertised context.

          Initial context goal: investigate 32K where model architecture, KV size, and speed allow it.
          Quantized KV cache can reduce memory use when the backend/model supports it and quality remains
               acceptable.
          Reuse prefix cache where it is safe and useful; manage eviction and session memory explicitly.
          Context length must be a real runtime-supported value, not just a UI setting.


        8.8 Speculative decoding and multi-token prediction
        Evaluate speculative decoding or model-native multi-token prediction only when the model and backend
        support it. Measure draft acceptance rate, verifier cost, extra memory, first-token delay, and sustained
        decode speed. A draft model can consume scarce VRAM/RAM and may slow generation if acceptance is low.


        8.9 The fast-path rule

         PRIMARY EXECUTION RULE The everyday fast path should keep the normal per-token working set resident in
         GPU memory and/or RAM as much as possible. SSD is the persistent model pool and a background source for
         rare or prefetchable pieces - not the default place from which huge amounts of active weights are fetched for
         every token.

        10. NECS: Neural Error-Correction Sidecar
        10.1 Purpose
        NECS is an experimental capability-preservation system. The idea is to use a compressed neural backbone
        for speed and memory efficiency, then attach small, selective correction data that may recover specific
        behavior lost during compression. The correction is a research hypothesis, not a guaranteed feature.

        10.2 Behavior-first compression
        Instead of optimizing only for tensor error or file size, evaluate which tasks become worse after each
        compression step. Capability areas include mathematics, science, programming, multi-step reasoning, multi-
        file software engineering, debugging, 3D development, instruction following, and reliability.


        10.3 Low-rank correction concept
        For an original weight matrix W and an approximated/quantized matrix Wq, define the difference as ΔW =
        W - Wq. A low-rank approximation may represent part of that difference as ΔW ≈ A B. The corrected output
        becomes Wq x + A(Bx). This can reduce the size of a correction relative to storing the full residual, but adds
        extra operations and memory access.

         CRITICAL TRADE-OFF A correction can improve quality while reducing speed. NECS is worthwhile only when
         the quality gain is repeatable, the correction is small enough, and end-to-end verified task performance
         improves after accounting for its runtime cost.




        10.4 How candidate corrections are discovered
          Run a fixed benchmark suite against a reference configuration and one or more compressed variants where
               possible.
          Find repeatable regressions, not one-off bad answers.
          Localize the likely source to layers, tensor groups, or quantization choices using offline analysis and controlled
               experiments.
          Test a correction on held-out data to avoid overfitting the benchmark examples.
          Measure quality gain, latency, extra memory, and whether the correction generalizes across prompts.


        10.5 Teacher-independent recovery
        ECLIPSE should not rely on the full-precision giant model being available at runtime. Potential sources of
        evidence include public datasets, independently verified math problems, Python execution, compilers, unit
        tests, Three.js runtime tests, documented APIs, and optional external reference outputs if a user has access.
        These can identify errors and support external verification without requiring the original model to answer
        every question.

        This does not mean an external tool can recreate arbitrary neural knowledge lost by compression. Some
        capabilities may not be recoverable with small correction modules. ECLIPSE must be willing to conclude that
        a compressed variant cannot preserve a desired capability at the required speed.


        10.6 Sidecar management
          Sidecars are optional, small, versioned, and separate from the base model.
          Load only when a tested task profile or verification signal justifies them.
          Cache correction data only within the resource budget.
          Record which model hash, quantization recipe, and benchmark set a sidecar was validated against.
          Never silently apply a correction to an incompatible model revision.

        11. Capability Watchdog and externalized intelligence
        11.1 Capability Watchdog
        The Watchdog decides when the fast path is sufficient and when additional verification or a slower
        enhanced path is justified. It should operate mainly at the task/workflow level, not add complex decision
        overhead to every generated token.

        Fast path
        Use the best known fast model configuration for ordinary conversation, drafting, and tasks whose risk is low
        and whose benchmark history shows reliable performance.

        Enhanced path
        For difficult or high-impact work, the Watchdog can request additional reasoning, a specialized tool, a
        second pass, execution tests, or a correction sidecar. It should weigh the expected quality benefit against
        latency and resource cost.


        11.2 Evidence signals
          Task type and complexity, known benchmark weaknesses, and prior success/failure history.
          Tool output such as compiler errors, failing tests, math checks, schema validation, or runtime exceptions.
          Consistency across independent methods or checks where available.
          Available memory, current latency, and whether the enhanced path would disrupt the fast path.
        A model’s own confidence statement is not sufficient evidence that an answer is correct. Confidence can be
        recorded, but independent checks should carry more weight when the task permits them.

        16. Research hypotheses and questions worth investigating
        The ideas below are research directions, not claims of invention or proven breakthroughs. Before calling a
        method novel, compare it with existing expert caching, dynamic precision, mixed-precision quantization,
        SSD-native inference, predictive prefetch, routing analysis, and model-correction research.


        16.1 Joint optimization of precision, placement, and cache
        Most decisions are often discussed separately: quantize weights, place some on GPU, cache frequently used
        experts, or prefetch likely next experts. ECLIPSE should test a joint planner that chooses precision, residency
        tier, and cache policy together under a fixed quality and memory budget. A smaller representation may
        allow more experts to stay warm, while a high-precision hot subset may preserve quality. The optimal
        combination must be measured.


        16.2 Static-first behavior-aware preparation
        Can static tensor metadata, weight statistics, architecture, and public workload data predict which layers or
        expert groups are most sensitive to quantization or placement? Start with offline inspection; later compare
        those predictions to actual runtime measurements. Measure whether the static analysis meaningfully
        reduces the number of expensive calibration runs.


        16.3 Prefetch value rather than raw prediction accuracy
        A prediction is useful only if it saves wall-clock time and does not waste too much bandwidth or memory.
        Evaluate prefetch by latency avoided, bytes wasted, cache pollution, and impact on actual decode speed - not
        simply prediction accuracy.


        16.4 Capability-specific correction
        Can a small residual or adapter restore a repeatable capability lost during compression without adding
        enough compute to erase the speed benefit? Test only after a specific regression is identified, use held-out
        data, and compare task throughput against the uncorrected variant.


        16.5 Task-aware scheduling
        Do coding, mathematics, and general conversation produce meaningfully different expert or memory access
        patterns? If yes, can lightweight profiles improve cache placement without overfitting to one prompt or
        forcing routing? This must be proven with repeated measurements.


        16.6 External verification as a quality multiplier
        For some task types, deterministic tests can compensate for a smaller reasoning model’s weaker self-
        checking. Test whether model plus tools can complete more verified software work than the same model
        alone, while including tool setup and repair time in the measurement.

        16.7 Research questions that could disprove ECLIPSE assumptions
          Can the target hardware keep enough of a given MoE model’s real selected working set resident to meet the
               speed gate?
          Does the CPU/GPU path provide enough compute once storage stalls are reduced?
          Can useful compression be made fast on this GPU generation, or do kernels become the limiting factor?
          Do static importance measures correlate with task-level capability retention?
          Can the Watchdog improve verified task success without making ordinary tasks feel slow?
          Does the complete system outperform simpler use of an existing inference backend enough to justify its
               complexity?

         SCIENTIFIC DISCIPLINE A negative result is valuable. If a proposed optimization does not improve sustained
         speed, quality, or verified work, ECLIPSE should document the result and move on instead of defending the idea.

        17.1 Implementation technology strategy
          Windows-native first. Do not require WSL or Linux for the core path.
          Use proven C/C++ inference backends and optimized kernels where needed; use a high-level language for
               orchestration, analysis, UI integration, and experiment automation when suitable.
          Pin dependencies and record exact versions. Prefer official projects and release channels.
          Isolate parsers and model-processing steps so malformed or untrusted model files cannot freely execute code.
          Make each operation resumable or safely restartable when processing multi-gigabyte files.


        18. First prototype: the smallest useful ECLIPSE
        The first prototype should prove the most distinctive premise: ECLIPSE can understand a model too large to
        run on the user’s computer. Do not begin with MoE caching, NECS, a 3D dashboard, or a custom inference
        engine.


        Prototype A - Static Model Inspector
         1. Create a small Windows project with a clean command-line entry point and a simple status report.

        Once the Atlas exists, calculate estimated storage and memory needs for candidate precisions, KV cache
        options, and residency tiers. Provide a “why it may fail” section. Do not produce unsupported tokens/second

        Prototype C - One working inference path
        Only after A and B work, integrate one established backend, one model known to be supported, and one
        measured configuration. The purpose is to establish the actual runtime baseline and validate that the model
        package and execution manifest are correct.

         WHY THIS ORDER Static inspection solves the immediate blocker without asking the computer to perform the
         impossible. It also creates the facts needed to decide which model and runtime path are worth trying next.




        19. Free, safe, and maintainable project rules
          Free-first: no mandatory subscription, paid API key, hosted inference endpoint, or proprietary cloud
               dependency.
          Local-first: the core model inspection and local inference workflow runs on the user’s Windows PC.
          Optional remote reference only: any remote inference or API-assisted evaluation is opt-in, clearly labeled, and
               never required to use ECLIPSE.
          Official sources: download runtimes, drivers, libraries, and releases from official or well-established project
               channels.
          Pinned dependencies: record versions and hashes where practical; avoid floating “latest” installs in
               reproducible builds.
          Least privilege: avoid administrator rights unless a clearly explained feature truly requires them.
          Original preservation: never edit the source checkpoint; write prepared variants separately.
          Safe file handling: do not execute code embedded in model files; treat imported artifacts as untrusted data.
          Privacy: keep prompts, logs, and model paths local by default; let the user inspect what a diagnostic bundle
               contains before sharing.

        20. Research references and interpretation notes
        The following sources informed the current plan and were checked for this version on November 3, 2026.
        They are reference points for design and comparison, not proof that the same performance is achievable on
        the target computer.


        20.1 Colibri: hierarchical MoE inference and benchmarks
        The Colibri project describes an inference engine that places hot experts on GPU, warm experts in RAM, and
        cold experts on NVMe storage. Its benchmark documentation explicitly distinguishes cold decode from full-
        resident operation. One documented setup reports approximately 11 GB of disk reads per token on a cold
        path and approximately 0.05-0.1 tok/s under a roughly 1 GB/s drive ceiling; a separate six-RTX-5090 full-
        resident experiment reports roughly 5.8-6.8 tok/s. These results illustrate the importance of residency and
        the danger of cold per-token reads. They are not direct forecasts for an RTX 2060 Super.
        Colibri official repository - https://github.com/JustVugg/colibri

        Colibri benchmark notes - https://github.com/JustVugg/colibri/blob/main/docs/benchmarks.md


        20.2 SSD-LLaMA research (September 16, 2026)
        The paper “SSD-LLaMA: SSD-Native Inference for Trillion-Parameter MoE at 1+ Token/s on a Consumer PC”
        studies SSD-native expert delivery, three-tier storage management, and CPU-GPU hybrid execution. Its
        abstract reports greater than 1 token/second for a trillion-parameter model with one RTX 5090 and no more
        than 32 GB RAM. This is an important research direction for ECLIPSE, but its hardware and implementation
        differ substantially from the user’s RTX 2060 Super and i7-8700K. The result demonstrates a research path,
        not transferability.
        SSD-LLaMA paper on arXiv - https://arxiv.org/abs/2609.18110


        20.3 llama.cpp: established inference infrastructure
        The official llama.cpp README lists CPU SIMD support, custom NVIDIA CUDA kernels, Vulkan, multiple
        quantization formats, and CPU/GPU hybrid inference. This supports the strategy of reusing mature inference
        infrastructure where model support and hardware compatibility are confirmed, while ECLIPSE focuses on
        inspection, planning, orchestration, and verification.
        llama.cpp official repository and backend overview - https://github.com/ggml-org/llama.cpp


        20.4 How to read the research claims
          A result on an RTX 5090 is not an estimate for an RTX 2060 Super. Different GPU generations, memory sizes,
               bandwidth, kernels, and CPU platforms matter.
          A high benchmark on one model does not establish support for all architectures or quantization formats.
          A peak result, warm-cache result, or short test does not prove sustained interactive performance.
          A model’s total parameter count alone cannot tell us its active compute or memory traffic.
          Research papers and project benchmarks should guide experiments, not replace measurements on the target
               computer.

        Final engineering position
        ECLIPSE should begin by understanding models that the computer cannot run, not by trying to force those
        models into memory. Static inspection is the entry point. A compatibility and feasibility planner turns the
        resulting facts into a realistic execution plan. Preparation creates reversible variants. A proven inference
        backend provides the first working runtime. Only then should ECLIPSE add deeper runtime tracing,
        predictive residency, advanced compression, NECS, and task-level intelligence management.

        The hardest requirement is not storing a very large model. It is delivering the weights and computation
        needed for each token fast enough, while preserving useful capabilities and keeping the computer
        responsive. If the selected model demands more data movement or compute than the PC can sustain,
        software cannot simply wish that bottleneck away. The project must find model-specific ways to reduce the
        active working set, use better representations, exploit compatible kernels, and verify that every optimization
        actually helps.

         NORTH STAR Maximum verified useful intelligence at a speed that feels interactive - with no hidden
         substitution of model behavior, no unmeasured claims, and no requirement that the original oversized model
         run locally before ECLIPSE can study it.
