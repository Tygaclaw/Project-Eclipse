I think we should aim much higher than simply getting Qwen to follow a few instructions. We should build a complete capability-amplification system around Qwen3.5-9B: one that can research, plan, use tools, understand existing projects, write code, test it, diagnose its own failures using real evidence, remember verified corrections, and keep working until it meets defined requirements.

There is a way to push this model dramatically further than its raw capabilities. But I want to be precise about what we're trying to achieve.
1. The goal: make a 9B model behave like a much larger system
There are two different things we need to distinguish:
- Model intelligence: The underlying knowledge, reasoning ability, generalization, and learned capabilities inside the model's 9 billion parameters.
- System intelligence: What the model can accomplish when surrounded by tools, documentation, memory, planning, execution, feedback, and verification.
We cannot turn nine billion parameters into seventy billion parameters through prompting, MCP servers, or an agent harness. The underlying model still has its own limits.

But we can build a system that lets it accomplish tasks that would otherwise require a substantially more capable model.

For example:
Without a harness	With the system we're planning
Guesses how a library works	Retrieves the correct, current documentation
Writes code and assumes it works	Runs it, tests it, and fixes failures
Forgets previous mistakes	Retrieves previously verified corrections
Tries to solve a huge task in one response	Breaks it into smaller, testable objectives
Gets lost in a large project	Maintains project maps, plans, and checkpoints
Says something is correct	Must provide actual verification evidence
Repeats the same failed approach	Detects repeated failures and changes strategy

The important distinction is that we're not trying to trick the model into thinking it is smarter. We're giving it capabilities that make its mistakes less likely to become finished results.

Our target should be a highly capable local engineering and research agent, not a chatbot with a really long system prompt.
2. What the research actually tells us
I found several particularly relevant pieces of research and technical documentation.
A. Tool-assisted verification can dramatically improve small models
Especially important
The 2026 ICLR paper T1: Tool-integrated Verification for Test-time Compute Scaling in Small Language Models investigates exactly the kind of approach we're interested in.

Its approach is to use external tools to filter and check possible answers, then use the smaller model to make the final judgment.

One particularly interesting result: their tool-integrated method allowed a Llama 3.2 1B model, with test-time scaling, to outperform a significantly larger Llama 3.1 8B model on the paper's mathematics experiments. The authors specifically found that small models struggled to verify things requiring memorization, such as calculations and factual checks, even after knowledge distillation. 
ICLR Proceedings


What this means for ECLIPSE: We should stop asking Qwen to remember or independently verify everything. We should give it reliable ways to obtain and check the information.

For coding, that means actual tests, compilers, type checkers, runtime output, and documentation.
B. Asking the model to check its own work is not enough
This is something I want us to take seriously.

A critical survey of LLM self-correction research, published in 2025, found that self-correction is not consistently effective when a model simply evaluates its own answers. It works much better when the model receives reliable external feedback. 
TACL


In other words:
- Qwen writes code.
- Qwen says the code looks correct.
- Qwen rewrites the code because it thinks it found a problem.
That is not a reliable verification system.

Instead:
- Qwen writes code.
- Python executes it.
- The tests identify failures.
- Qwen receives the actual errors.
- Qwen makes a correction.
- Python runs the tests again.
The tools become the source of truth. Qwen becomes the problem solver.
C. The model itself is already capable of more than its raw output might suggest
Qwen's published Qwen3.5-9B benchmark table reports:
Benchmark	Published score
GPQA Diamond	81.7

BFCL-V4	66.1
TAU2-Bench	79.1
DeepPlanning	18.0

These are the model publisher's reported results, not an independent guarantee of how it will perform on your PC. Different benchmarks also measure different abilities. Still, this gives us useful starting points: the model has meaningful coding and tool-use capabilities, but planning deserves particular attention in our own evaluations. 
Hugging Face


Qwen's own model documentation recommends Qwen-Agent for building agent applications around Qwen3.5. It supports function calling, MCP, and external tools. 
Hugging Face+1


We should keep that in our back pocket as a possible alternative if our existing Claude Code integration proves unreliable. We don't need to install another framework before testing what we already have.
D. The way we connect tools to the model matters enormously
I found something particularly relevant to our current setup.

Claude Code communicates using the Anthropic Messages API. Current llama.cpp documentation includes an Anthropic-compatible /v1/messages endpoint, including tool definitions and tool-use support when Jinja is enabled. However, llama.cpp explicitly cautions that it does not guarantee complete compatibility with the Anthropic API specification.

There have also been Qwen3.5-specific tool-calling problems reported in llama.cpp.

One August 2026 issue documented cases where Qwen3.5-based models failed to initiate tool calls when presented with many tools and very large system prompts. Its examples involved 20 or more tools and prompts exceeding 10,000 tokens. Another report documented parsing problems involving multiple XML tool calls. 
GitHub+1


This is important because more tools do not automatically mean a smarter agent.

We should dynamically expose only the tools relevant to the current task instead of dumping every available tool into the model's prompt.

3. The architecture I recommend building
I want to retain the things you've already installed and build around them instead of creating redundant systems.
ECLIPSE — Capability Amplification Architecture
Qwen3.5-9B

The reasoning and decision-making engine


1. Capability Watchdog

Determines task difficulty, risk, required tools, and how much verification is needed.

2. Planning Engine

Breaks complicated objectives into manageable tasks with explicit completion requirements.

3. Research and Context Engine

Retrieves relevant documentation, repository information, project context, and verified memory.

4. Execution Engine

Uses existing Claude Code capabilities, MCP tools, PowerShell, Git, and project files.

5. Verification and Recovery Engine

Runs tests, checks results, identifies failures, and directs corrective work.

6. Learning and Correction Memory

Records recurring mistakes and verified fixes for future tasks.


Verified Result

Completed work, test evidence, project state, and saved lessons.

The model remains the central decision-maker. The surrounding system gives it better information, better tools, and reliable feedback.
Here's how I would implement each part.
1. Capability Watchdog
This is the system that decides how much assistance a task needs.

A simple question shouldn't require six agents, a planning document, and twenty tool calls.

But a request to build an entire application absolutely should receive a more sophisticated workflow.

The watchdog should examine things like:
- How many files or subsystems are involved?
- Does the task require current documentation?
- Does it involve unfamiliar APIs?
- Could an incorrect action destroy data or expose private information?
- Are there objective ways to test the result?
- Has Qwen previously failed at something similar?
It then selects the appropriate workflow.

For example:
Task	Workflow
Explain a Python function	Normal response
Fix a small bug	Inspect → Fix → Test
Build a multi-file application	Plan → Implement → Test → Review
Modify a large existing project	Map → Research → Plan → Implement → Regression test
Unfamiliar technology	Research documentation before coding

This prevents the harness from wasting resources on simple tasks while still giving complicated tasks the attention they need.
2. Planning Engine
This is one of the most important additions.

Before attempting a complicated project, Qwen should produce a structured plan containing:
- The actual objective.
- Required features and constraints.
- Files and systems that need modification.
- Dependencies between tasks.
- Acceptance criteria.
- Potential failure points.
- How each feature will be tested.
It should also maintain a task checklist and mark work complete only when evidence supports that decision.

For large projects, I want it to work on one manageable objective at a time, not attempt to generate an entire application in one enormous response.

Your previous Reading List Manager experiment demonstrated why this matters: the 10,000-token generation limit interrupted the response, and the generated implementation contained several logic and interface defects. We should have the model write files directly through its tools, then test them, rather than printing an entire application into a chat response. 
3. Research and Context Engine
We already have two valuable pieces of infrastructure:









Context7

Current, version-specific library documentation and examples.

Context7 Claude Code documentation











GitHub MCP

Repository files, code searches, issues, commits, branches, and pull requests.


I don't want to recreate either one.

Instead, ECLIPSE should decide when to use them and retrieve only the information that matters.

For example, if Qwen is writing a Three.js feature, it should retrieve the relevant Three.js version documentation and inspect the actual project structure before making changes.

It shouldn't invent API methods based on old training data.
4. Execution Engine
This is where Claude Code comes in.

We should reuse its existing abilities to interact with files, execute commands, edit code, and work with MCP servers.

I want the model to work through a controlled sequence:
1. Inspect the relevant files.
2. Understand the existing implementation.
3. Make a small, targeted change.
4. Run the appropriate command or test.
5. Examine the actual output.
6. Continue based on the result.
One important rule: don't expose twenty different tools when the task only needs three.

The earlier llama.cpp reports make a good case for keeping the available tool schemas and system instructions small. For the first version, I would use one tool call at a time and only experiment with parallel calls after sequential calling is reliable.
5. Verification and Recovery Engine
This is where we can get some of the biggest improvements.

Qwen should never be allowed to declare an application complete simply because it has finished generating code.

For a Python application, for example, the system could automatically run:
- Unit tests.
- Integration tests.
- Syntax checks.
- Type checks when appropriate.
- Linting.
- Security checks when relevant.
- A final review of the Git changes.
For a Three.js project, the workflow might include:
- Dependency checks.
- Build checks.
- JavaScript error detection.
- Runtime tests.
- Feature-specific acceptance tests.
When a failure occurs, the system should preserve the exact error, identify the likely cause, make the smallest reasonable correction, and rerun the failed test.

I also want loop detection. If it tries the same failed approach repeatedly, the system should recognize that, stop, reconsider the strategy, and avoid wasting thousands of tokens.

The model's opinion is not proof. The results of the tests are proof.
6. Correction Memory
This is different from simply saving conversation history.

I want ECLIPSE to have a permanent library of verified lessons.

For example, from the previous Reading List test, useful correction entries could include:
Observed mistake	Stored lesson
Service uses an uninitialized book collection	Initialize or load storage before CRUD operations
Deserialized book receives a new UUID	Preserve the persisted identifier
Storage loader passes the wrong JSON level	Validate the storage schema and object hierarchy
CLI passes strings instead of enums	Normalize and validate input types
Tests expect files that aren't created	Align initialization behavior and test expectations

These are examples of lessons derived from that failed implementation, not generic rules that should be blindly applied to every application.

Each correction should contain:
- The original problem.
- The actual root cause.
- The verified fix.
- A reproduction test.
- The projects or languages where it applies.
Only corrections confirmed by tests should become permanent knowledge.

That last requirement matters enormously. Otherwise, the model could remember one of its own incorrect explanations and repeatedly make the same mistake.

4. The additional intelligence-boosting techniques
Beyond those six primary components, I want to experiment with several techniques that can help us push the model further.
Test-time compute scaling
Instead of always generating one answer and accepting it, give difficult tasks additional reasoning and evaluation opportunities.

For example, when a coding task is genuinely difficult:
1. Generate a proposed solution.
2. Examine it against the acceptance criteria.
3. Run independent tests.
4. Identify weaknesses.
5. Generate an alternative approach when necessary.
6. Compare results and select the solution that actually works.
We should not do this on every request. It consumes time and tokens, and multiple answers from the same model are not truly independent.

But for difficult tasks where we have reliable tests, this is worth experimenting with.

The T1 research provides a scientific reason to prioritize this approach, particularly when external tools can check what a small model cannot reliably remember. 
ICLR Proceedings

Specialized skills
Rather than giving Qwen one enormous prompt containing instructions for everything, we should create focused skills that load only when needed.

Examples:
- Python development.
- Debugging existing code.
- Three.js development.
- Game development.
- Git and GitHub workflows.
- API integration.
- Software testing.
- Security review.
Each skill should contain concise, tested procedures and relevant project conventions.

This can improve consistency without cluttering every request.
Multiple roles and independent checking
We can experiment with separate roles:
- Planner.
- Implementer.
- Reviewer.
- Tester.
These roles could use the same Qwen model, but I don't want to pretend that having four copies of the same model gives us four independent brains.

Their main value is separating responsibilities.

The actual verification should still come from external tools, test results, and deterministic checks.
Optional frontier-model fallback
There is another route worth keeping available.

We could eventually have an optional model-routing system:
- Qwen handles ordinary work locally.
- The watchdog identifies tasks beyond its measured capabilities.
- With your permission, a stronger cloud model can help with especially difficult tasks.
This would make the overall system considerably more capable, but it would not mean the local Qwen model itself had become equivalent to Opus or GPT.

I would keep this completely optional, with private information excluded unless you explicitly approve sending it externally.

Optimization	Expected benefit	Priority

A few important details:

Context length is not intelligence. Qwen3.5 supports a native 262,144-token context, but we should not automatically send enormous amounts of information to every request. We should retrieve the relevant parts of a project and maintain concise checkpoints.

Higher quantization isn't automatically better for your PC. Your current Q4 model already uses much of the available GPU memory. A Q5 version might improve quality slightly, but only makes sense if it fits without creating a substantial CPU-offloading performance penalty.

Fine-tuning should come later. Once the correction system has accumulated a sufficiently large collection of verified examples, we can investigate training a LoRA adapter. That could improve recurring behaviors and specialized tasks, but it won't magically give the model the general reasoning capacity of a much larger model. With 8 GB VRAM, it also needs careful feasibility testing.

I don't want to start messing with a working model configuration before we have the evaluation system to tell whether a change actually helps.

6. How we'll prove that ECLIPSE is actually making Qwen smarter
This might be the most important part of the entire project.

We need an evaluation system that prevents us from confusing a more elaborate harness with a genuinely more capable one.

I want to preserve the four categories from your existing evaluation roadmap:
Test	What it measures
Multi-file feature development	Can it build an application across multiple files?
Runtime debugging	Can it diagnose and repair existing failures?
Existing codebase modification	Can it understand interconnected code and modify it safely?
Three.js/game development	Can it handle more complicated interactive projects?

We should also retain the Reading List Manager as a regression test and track whether the specific mistakes it made are actually eliminated. 

For every test, record:
- Whether it succeeded on the first attempt.
- Whether it succeeded after correction.
- Whether all independent acceptance tests passed.
- Whether it introduced regressions.
- How many tool calls and repair attempts it needed.
- How long it took.
- Whether it made unsupported claims about successful work.
We should run the same tasks against:
1. Raw Qwen3.5-9B.
2. Qwen with the basic Claude Code tool loop.
3. Qwen with the complete ECLIPSE harness.
That will show us exactly which components are responsible for improvements.

I would also preserve the test cases so that a future change cannot quietly break something that previously worked.
Our definition of success
- The model reliably calls the right tools.
- It understands existing project structures.
- It produces working implementations.
- It catches its own mistakes through external evidence.
- It stops repeating failed approaches.
- It remembers verified corrections.
- It does not expose private information.
- It only reports completion when the required checks pass.

7. The implementation roadmap I recommend
I would build this in the following order. The order matters because we need to verify the foundation before adding intelligence layers on top of it.
1. Phase 1 — Prove the tool connection
   
   Verify that Claude Code is genuinely communicating with your local Qwen server, that Qwen can make structured tool calls, and that Context7 and GitHub MCP actually execute and return results.
   
   We should also test whether the current connection uses the correct API protocol, rather than relying on the previous direct /v1/chat/completions tests.
2. Phase 2 — Establish the baseline
   
   Preserve the current model configuration, organize the evaluation tasks, and measure its raw performance and basic tool-assisted performance.
3. Phase 3 — Build the ECLIPSE core
   
   Implement the Capability Watchdog, Planning Engine, Research/Context Engine, Verification Engine, Recovery Engine, and Correction Memory.
   
   Reuse the existing Claude Code extension system, GitHub MCP, Context7 MCP, and local tools wherever possible.
4. Phase 4 — Add advanced reasoning workflows
   
   Introduce additional verification passes, alternative solution generation, specialized skills, project checkpoints, and better context management.
5. Phase 5 — Evaluate and improve
   
   Repeat the full evaluation roadmap, identify the remaining weaknesses, and improve the exact components responsible for them.
6. Phase 6 — Model-level optimization
   
   Experiment with quantization, inference settings, speculative decoding, and—only once we have enough verified training examples—potentially a specialized LoRA adapter.

My final recommendation
I would not build another giant AI framework, another memory platform, or another layer of agents that duplicates Claude Code.

I would build a lightweight but extremely capable system around the infrastructure you already have.

The biggest gains are likely to come from four things:
1. Better planning: Stop the model from attacking complicated objectives without understanding them.
2. Better information: Give it current documentation and actual project context.
3. Better verification: Make it prove that its work functions.
4. Better learning: Make sure verified mistakes don't keep happening.
Those four things, combined with a carefully designed tool loop and targeted test-time compute, give us a realistic opportunity to push this model far beyond what it can accomplish on its own.

And I want to emphasize something: we shouldn't declare ECLIPSE finished just because all its components have been implemented. We should keep testing it, finding weaknesses, and improving it until the measured results stop improving or we hit a genuine model limitation.

The immediate next step is Phase 1: inspect the current Claude Code MCP connections and prove that your Qwen server can execute a real, harmless tool call. We should do that before writing any new ECLIPSE components.
